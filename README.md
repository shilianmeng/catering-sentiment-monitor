# 餐饮舆情监测与研判平台（面试作品版）

一个能一键跑起来的餐饮舆情系统：采集 → 打标 → 去重聚合 → 烈度评级 → 预警 → 处置 → 报告导出。

- **品牌不写死在代码里。** 一个客户总部 = 一条「监测主题」，品牌名、别名、事件议题规则、门店清单都放在 `topic` 表的 `brand / entities / event_rules` 字段里，换客户只改数据。
- **演示客户是虚构品牌「香满园」**，舆情传播链路为模拟数据；另有**越秀区「双公示」真实处罚数据**（235 条、217 个主体）支撑「主体风险」页，证明能接真实官方数据。
- 数据来源与字段规范见 [`docs/00-数据来源与字段规范.md`](docs/00-数据来源与字段规范.md)。

## v2.1 改了什么

| 改动 | 为什么 |
|---|---|
| 品牌、别名、门店、事件规则从代码移到 `topic` 表 | 原来只认「香满园」一家，换客户要改代码 |
| 凭据外置：key / 密码只从 `backend/.env`、`backend/secrets.local.json` 或环境变量读 | 代码里原来硬编码着大模型 key，仓库一外发就泄露 |

| 依赖锁定版本、一键启动脚本、启动时自动建库补列、演示库自动灌种子 | 换台机器要能跑起来，这是作品集的基本盘 |
| 数据来源分三类、字段与证据留存写成规范 | 报告要经得起「你这数据哪来的」这一问 |

## 启动

一键（推荐，面试演示用这个）：

```powershell
.\start.ps1            # 起后端 8091 + 前端 5180
.\start.ps1 -Reset     # 先重置舆情演示表（删表重建、灌种子、回到 T0）再启动；
                       # 官方处罚记录和原文快照不删，重置前自动整表备份、重置后逐条核对
.\stop.ps1             # 关掉本项目占用的 8091 / 5180
```

脚本会先检查 Python 依赖、MySQL 3306 是否在监听，等后端 `/health` 通过后才起前端。

重置保留 `auth_session`、`source_snapshot`、`official_record`，重建舆情演示表并回到 T0；品牌/门店关联会重新建立。`start.ps1 -Reset`（等价于在 `backend/` 运行 `python -m app.engine.demo --reset`）额外执行 `guarded_reset()`：先将 `official_record` 整表备份到 `backend/data/backups/`，再按 `record_key` 核对业务字段和 `revision`，不比较允许重新挂接的 `topic_id/store_id`；发现旧记录丢失或字段改变时返回非零退出码，启动脚本停止。网页「重置演示」调用普通 `demo.reset()`，保留同样三张表，但不会自动备份或逐条核对。这不是自动回滚，也不是快照文件备份。

手动启动：一个终端在根目录运行 `python run.py`；另一个终端进入 `frontend/` 运行 `npm run dev`。

然后浏览器打开 <http://127.0.0.1:5180>。后端接口为 `http://127.0.0.1:8091/api/v1`，接口文档为 `/docs`。首次启动会自动建库（`CREATE DATABASE IF NOT EXISTS`）、建表、灌入演示数据（T0 批次）；老库启动时自动补新表/新列，不删数据。

> 本地前端 5180、后端 8091，只监听 127.0.0.1。数据库使用 MySQL 8.0 / InnoDB / utf8mb4。Vite 开发服务器不作为生产服务器。

## MySQL 配置

使用专用业务库，避免与其他应用共用库。数据库管理员先执行：

```sql
CREATE DATABASE YuQing CHARACTER SET utf8mb4 COLLATE utf8mb4_bin;
-- Windows 下 MySQL 会显示为小写 yuqing，是同一个库。
-- 本机演示用 root 账号；换专用账号时授予 YuQing.* 的建表、删表、查询、插入、更新、删除权限。
```

**真实凭据通过外置配置加载，源码不保存模型 key；MySQL 的 `root/root` 是本地演示默认值。** 两种放法，二选一：

- `backend/.env`（推荐）：`Copy-Item backend\.env.example backend\.env` 后填值；
- `backend/secrets.local.json`：`{"openai_api_key": "", "mysql_password": "root"}`，照 `backend/secrets.example.json` 抄一份。

两个文件都已被 `.gitignore` 排除，不会进版本库；同名环境变量优先级最高。

| 项 | 默认值（不建 .env 时） |
|---|---|
| 地址 | 127.0.0.1:3306 |
| 数据库 | YuQing（不存在会自动建） |
| 账号 / 密码 | root / root |

同名环境变量 `YUQING_MYSQL_HOST / PORT / DATABASE / USER / PASSWORD` 优先于 `.env`。换机器或换账号时改 `.env` 即可，代码不用动。连接失败会明确报错，不会回退 SQLite。MySQL 建表/删表会隐式提交，因此「重置演示」不是可回滚的事务；仅用于专用演示库。

## 大模型（可选）

报告和回应话术可以调用 OpenAI 兼容接口生成。**key 不在代码里**：写在 `backend/.env` 的 `OPENAI_API_KEY`，或设同名环境变量。

```powershell
# backend/.env
OPENAI_API_KEY=sk-...
OPENAI_MODEL=gpt-4o-mini
```

不配 key 也能跑：自动降级为模板生成，页面上标注「模型生成 / 模板生成」。所有评分、分级、预警规则都是确定性计算，不依赖模型。

## 测试

```powershell
cd backend
python -m unittest discover -s tests -t . -v
```

## PDF 中文字体

导出 PDF 依次查找 `C:\Windows\Fonts\simhei.ttf`、`msyh.ttc` 等中文字体；都找不到时接口返回 500 并提示原因，Markdown 导出不受影响。

## 与设计方案的差异

- 图表使用本地打包的 ECharts，不依赖运行时 CDN
- 多一张 `response_draft` 表（话术草案留痕，共 15 张表，v2.1 增加 `auth_session` 会话表、v2.2 增加 `store` / `source_snapshot` / `official_record`）；`content` 表多 `dup_of` 等字段记录水军合并关系
- 多了 `/api/v1/clock`、`/api/v1/logout` 两个辅助接口
- T3 时 ev001 烈度 96 分（最初设计示例为 92 分，当前设计文档已同步为 96 分），等级同为 S

## 部署边界

当前是面试作品：舆情传播链路使用模拟数据，官方处罚链路已接入真实数据。凭据已外置，会话已持久化；生产上线仍需替换演示账号、接入合规的真实舆情来源和通知渠道、配置 HTTPS、数据库与快照备份及反向代理。Vite 开发服务器不用于生产。前端执行 `npm run build` 后部署 `frontend/dist/`，配置 SPA 路由回退及 `/api` 到后端的代理；后端独立运行。
